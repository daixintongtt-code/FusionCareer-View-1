# 学生端简历 AI 分段接入

本次前端复用现有简历解析链路，不新增模型或算法服务调用方式。目标为上传后直接展示 AI 已识别的各段经历，已有文件也可重新解析。

## 前端调用

- 上传：`POST /api/user/resume/file/upload`，FormData 为 `file`、`updateProfile`。`updateProfile=true` 沿用既有 AI 更新资料和在线简历语义；未勾选时仍仅上传文件。
- 已有文件重新解析、失败重试：`POST /api/user/resume/file/{id}/parse`。
- 解析结果沿用 `parseStatus: SUCCESS/FAILED`；成功后重新请求 `GET /api/user/resume/get`，不把提示文案当作简历正文。
- AI 同时更新个人资料，成功后也需重新请求 `GET /api/user/profile/get`，只有资料与正文都读取成功才提示解析完成。
- 保存仍为 `PUT /api/user/resume/save`，九个字段保持原始字符串，包括 `internship`、`campus`、`education`。阅读分组不改写已加载的原文。

文件重新解析会按现有服务规则更新资料与在线简历。请求进行中互斥保存、上传与其他解析，暂时禁用正文编辑；失败保留当前文本。如果 AI 处理成功但随后读取正文失败，保留旧文本供查看，锁定编辑、保存、上传与解析，避免旧内容覆盖新结果；“重新加载正文”只重试 GET，成功后解锁并切回阅读预览。首次读取失败同样阻止保存空白表单。

“我的资料”也参与同一请求互斥：解析、上传、资料或正文读写期间，资料表单通过 disabled 与 inert 禁用原生输入和自定义选项，保存入口再次检查锁定状态。资料正在保存时也不能发起上传、解析或正文保存。如果资料 GET 失败，保留当前值并锁定资料编辑/保存及简历修改，两个页面均提供“重新加载资料”；该操作只重试资料 GET，失败继续锁定，成功替换为最新值后恢复。首次资料读取失败时同样阻止提交空表单。

## 已存在的算法输出约定

关联算法仓库 [FusionCareer-Algorithm 的261013版说明](https://github.com/chenxin1209/FusionCareer-Algorithm/blob/702440f1c5b2153d0f9fdfd6ba7c573eff82a3b6/resume_parser/README_261013.md) 已包含自动经历识别。模型中间结果要求每段经历为单独数组元素，最终兼容接口仍返回字符串：

```text
甲公司 | 内容运营实习生 | 2026.01—2026.03
整理选题与资料；协助稿件编辑

乙公司 | 项目实习生 | 2025.07—2025.09
维护项目进度；整理复盘材料
```

前端对教育、实习和校园字段按空行分隔整段，块内单换行保留。支持 LF、CRLF、CR；其他字段按行显示。字面量反斜杠+n、日期或标点不会被前端猜测为经历边界。显示采用文本插值，不执行模型返回的 HTML。

## 必须核对的真实接入条件

- 算法旧入口 `resume_parser.main:app` 和新版 `resume_parser.main_261013:app` 并存。新版健康检查 `/health` 应返回 `resume_parser_version=261013`；前端不直接调用内部算法路由或健康检查。
- 实际 Java 后端需衔接已部署的新版或等价输出能力，保留存储和 GET 响应中的空行。公开候选 Java 分支与算法路由存在版本差异，不能据此推断生产环境已对齐。
- 若旧文本没有分隔，应通过已有文件重新解析获取可靠分段，不由浏览器按日期猜测。是否启用新版服务由实际维护方确认，本次不修改部署配置。

验收应以脱敏多段简历经过真实上传/重新解析后返回的正文为准，确认两段经历之间有空行且段内标题和职责换行未丢失。本地拦截响应只验证前端流程与格式兼容，不能证明线上 AI 已启用新版或解析准确率达标。
